# dsh-triggers

**结构化交接触发器**：把两个普通 session 绑成一个「执行 ↔ 审核」循环。执行者收尾有两种
方式——**自动送审 run**（handoff 交接默认）在回合**正常结束后**由宿主把该回合的最终回复
直接送审，执行者不需要调用任何工具；**工具 run**（非 handoff 绑定默认）仍调用 `trigger_signal`
提交交付。审核者以 `rework` / `pass` / `needs_user` **工具**回签，返工意见排回**同一个执行
session**。轮次有预算、可暂停/恢复/取消，一切推进都在宿主进程里完成——浏览器关着、没人
盯着也不中断。

产品形态是通用的「事件 + 模板 + 目标 session」：执行—审核循环是首个预设（一个规则组的
两条方向行共享生命周期与轮次预算）；模板由绑定引用并在启动时快照，浏览器首版只读展示。

## 循环语义

```text
启动（handoff 交接创建绑定与首个 run）
  └─ 第 N 轮：phase=awaiting-delivery（执行者工作）
       自动送审 run：最终回复 → turn/end(completed) → 直接送审（无需工具，见下节）
       工具 run：执行者调用 trigger_signal(runId, deliver, summary)
                  → turn/end(completed) → 审核 prompt 队列投给审核者
       （两类 run 需要用户决定时都调用 trigger_signal 提交 needs_user）
        → phase=awaiting-review
  └─ 审核者调用 trigger_signal(runId, rework|pass|needs_user, summary)
       rework 且 N < max  → 返工 prompt 排回执行者，N+1 轮开始
       rework 且 N = max  → paused-budget（保留待发返工意见；加预算可续）
       pass               → completed（执行者收到一条完成通知）
       needs_user         → paused-user（双方任一方都可提出）
```

硬性规则：

- **裁决只认工具**。审核者的 rework / pass / needs_user 与执行者的 needs_user 只能通过
  `trigger_signal` 提交；普通回复、step 结束、中间输出都不构成结论，模型忘叫工具 ≠ 通过。
  自动送审 run 里执行者的 `deliver` 只是可选项——正常结束回合本身即交付。
- **自动送审是受控的**。仅当：run 标记 `autoDeliver`（handoff 绑定默认开、非 handoff 绑定默认
  关；运行启动时快照，改绑定不影响在途运行）、该回合以 `completed`
  结束、执行会话没有**活动 goal**（goal 续轮的回合结束可能还有下一轮，不提前送审；
  goal 落定后的下一回合再送）、最终回复非空（取该回合**最后一条** assistant 消息——终稿
  为空或仅空白时视为无可交付内容，绝不回退用更早的中间输出）。
- **一个回合至多推进一个 run**。回合已为某个 run 显式提交信号时，其余 run 不再自动送审；
  同一执行会话有**多个** auto run 同时等待交付时，一条回复无法归属到具体任务，任何一个
  都不自动送审（各自收到一次有限提醒，由执行者用显式信号指明交付对象），绝不把同一份
  交付广播给多个任务。
- **只认本会话本回合**。信号记录提交者 session 与其 turn；只有**该 session 自己**的对应
  turn 结束才算数（双方回合号各自独立，对方同编号回合结束不推进也不打断）。该 turn 以
  `aborted` / `error` 等非 `completed` 结束 → `paused-error`，绝不按已交付推进。同回合重复同
  信号是幂等 no-op，换结论则拒绝；一个 session 的一个回合只能为一个 run 提交信号。
- **迟到即拒绝**。暂停/取消/完成后的 run 拒绝一切信号，旧轮次的信号叫不醒任何人。
- **最后一轮仍完整送审**。预算挡的是「第 N+1 次执行」，不是第 N 次审核。
- **暂停 ≠ 打断**。暂停/预算用尽只停自动交接，不 cancel 正在跑的 agent。

## 有限提醒（缺失结论的兜底）

回合正常结束但结论缺席时，宿主补**每轮每侧至多一次**的提醒（`nudge` 类投递；提醒发送
失败只记日志，不暂停 run）：

- **交付提醒**：工具 run 的执行回合结束却没提交信号 → 提醒调用 `trigger_signal` 交付；
  自动送审 run 的回合结束但最终回复为空（没有可送审的内容）→ 提醒补一条总结性最终
  回复；多个 auto run 同回合等待交付（归属不明）→ 各提醒一次。歧义提醒是**自包含**的专用指令（必须用 trigger_signal 指定 runId 交付），不附带常规规则块——auto run 的常规块写着「正常结束回合即自动送审」，与歧义场景恰好相反，混入会堵死唯一恢复路径。
- **审核提醒**：审核 prompt 已送达、审核者回合结束却没提交裁决 → 提醒提交
  rework / pass / needs_user。

提醒同样让位于活动 goal（goal 进行中不打扰）；同一轮内不重复。

提醒投递（含重启恢复与手动重投中的 nudge 记录）始终 best-effort：发送失败只标记该投递
failed，绝不把 run 置 `paused-error`。

goal 活动状态重启后会**从持久会话日志重新折叠**（见下节），不再是不持久化的已知限制。

## 可靠投递（原子提交 + 事务发件箱）

每次状态推进是一次**数据库式原子提交**：运行的新状态与本次转换欠下的全部待发消息
（含一次性铸好的 `requestId` 与**完整编排后**的 prompt 内容）合并进**同一条 run 记录、
一次持久写**。写入前崩溃——两者都不存在；写入后崩溃——两者都在。不存在「run 已推进到
等待审核、却没有对应待办投递」的半完成状态。

run 记录内嵌的待办队列即**事务发件箱（outbox）**：提交成功后才逐条发送；发送确认后
条目离开发件箱（`deliveries` 表退化为可重建的投影，服务 UI 历史与手动重投查询）。
发送失败把条目标记 `failed` 留在发件箱（等手动重投），非提醒类失败同时把 run 置
`paused-error`。重试/重启/手动重投全部复用原 `requestId`——宿主对已入队/已记录的
requestId 返回原接受而不重复插入，这正是补投幂等的契约。prompt 内容在提交时一次性
编排完成，任何重试都逐字重发同一段内容（重试绝不重新套用规则）。

**消费检查点**与状态转换**同一次提交**：每侧已消费的最高回合号记在 run 记录里，
无论该回合推进了运行还是被评估后跳过（暂停期间同样计数——暂停窗口里的回合在恢复后
不算新交付）。重启回放因此对每个回合恰好消费一次：第一轮的交付永远不会在第二轮的
状态下被重新解读。run 创建即初始化检查点；升级前写下的旧记录（无此字段）首次重启时
把日志已闭合的历史一次性视为已消费——迁移是**每 run 一次写、双侧合并**（分侧写旧快照
会互相覆盖），且**未决信号所属的回合除外**：那一回合保持未消费，交给回放按日志结局
补提交（completed）或异常暂停，绝不静默吞掉。

**同 run 串行**：信号、暂停/恢复/取消/续轮/重投、回合结束转换、投递结算都是对同一
run 记录的读-改-写，全部排在每 run 的串行链上、基于最新已提交状态计算——并发控制
（如取消撞上续轮）不会以后写覆盖复活前者。投递的网络发送在链外执行（宿主队列可能在
发送中同步回话，链内发送会自锁），结算回到链上。

重启恢复按序做四件事，绝不给用户已停下的运行补发消息：

1. **日志对账**：对每个仍在进行的 run，把双方会话的**持久日志**
   （`sessionController.inspect`）按事件时间合并成一条时间线（两侧日志因果交错，
   分侧回放会拿错轮次），把插件崩溃前没来得及处理的 `turn/end` 按**事发时点**（当时
   的 goal 状态、该回合最后一条 assistant 消息）补处理——检查点保证已消费的回合不
   重评，run 创建前的历史被基线挡住，绑定前的历史回合绝不误当交付。未决信号同样以
   日志为准：回合以 `completed` 结束 → 安全补提交；异常结束 → `paused-error`；
   回合仍在进行 → 保持等待（重启不再盲目暂停）。goal 活动、当前回合、最后回复的
   内存缓存也由此重建；初始化读取期间到达的实时事件**只缓冲、不预判**——日志基线
   播种完成后按到达顺序统一重放，boot 期回合的时点上下文（goal 状态等）以播种后的
   缓存为准，不会被空的预播种缓存冻结。新绑定（含重启后首次 bind）同样在 run 创建
   前从双方会话日志播种缓存——启动早于一切 run 的冷 goal 不会在首个完成回合误送审。
   播种区分**临时缓存**（任何实时事件都可能先建出来，不说明日志历史）与**已播种
   缓存**（从持久日志推导，带显式标记）：临时缓存不阻止播种，已播种的会话绝不被
   旧快照重复覆盖；同会话并发的播种**共享同一个进行中的读取**（后来的 bind／恢复
   等它落地，绝不当作已完成），读取期间到达的实时事件先缓冲，读取完成后以日志
   基线为底**只按序分发一次**——每个回合结束当场取自己的时点上下文（goal 状态、
   最后回复），缓冲里靠后的状态变化不会污染靠前回合的判断。恢复／重投唤醒暂停的
   运行前同样先在 run 串行链内播种双方会话（启动回放只覆盖当时的 active run），
   缓冲的回合排在运行复活之后，由复活后的运行按基线正确消费。
2. **投影重建**：deliveries 表行从权威 outbox 重导出——两表之间任何一次写入崩溃
   留下的分叉（如 failed 权威配 pending 投影、UI 丢失重投按钮）在重启时自愈。
3. **发件箱补投（带门控）**：pending 条目按原 requestId 补发，但只发给**当前状态仍
   接受它**的运行——会话类投递（start/review/rework/resume）要求运行 active 且轮次
   与阶段匹配；已取消/完成的运行只保留终局通知（notice）类的补发；用户/预算暂停的
   运行不自动补投会话类（恢复是用户的决定，与手动重投的规则一致）；failed 条目等
   手动重投；nudge 全路径 best-effort。
4. **旧数据兼容**：outbox 引入前写入 deliveries 表的 pending 行保持原恢复契约，
   同样受门控约束。

边界：原子性指**插件进程内单记录单写**——宿主 JSON 后端对一次 resolved write 承诺
崩溃耐久（临时文件 + fsync + 原子改名），跨表/跨记录仍无事务，因此本设计把状态与
待办合并在一条记录里而不是依赖事务。宿主未 flush 的事件（崩溃截断的日志尾巴）插件
无法感知，交给轮次预算与有限提醒兜底；多 DSH 进程共写同一存储不受支持。

手动重投**先恢复运行、后补发**（同 requestId）——对方收到 prompt 的那一刻运行已在
接收状态；补发再失败会重新暂停。三类投递被拒绝：已结束（完成/取消）的运行（不再
唤醒对方）；用户/预算暂停的运行（需先显式恢复）；**过期投递**（不属于当前轮次与
当前阶段的旧记录——重发会给对方过时的指令，其结论可能污染新轮次）。

状态只存宿主 `storageDomain`（`triggers` 域：templates / bindings / runs / deliveries）；
模型看到的一切（工具结果、投递 prompt）都在正常 session 日志里。

## GUI

会话顶部页签 **触发器**（`conversation.view`，id `triggers`，order 30，排在 Chat / Trajectory /
Spine Tree 之后）。只显示**当前会话参与**的循环：作为执行者或审核者任意一方出现，行上标出本
会话的角色。没有全局侧边栏入口，标题区也不再放操作 chip。

- 首屏只有标题和一条「N 个运行进行中」摘要（有运行在进行时才出现）。规则组一行只保留任务名、
  本会话角色与对方会话的关系、当前轮次和状态；自动送审、绑定状态、模板等低频信息下沉到折叠
  的只读配置里。
- 点开行只显示当前运行的原因和必要操作。失败/待发送投递（含具体错误、可用时的「重投」）与
  恢复入口保持直接可见，并排在普通历史之前。
- 历史、已送达投递和只读配置收在「详情」里，默认不展开；其他运行收在「其他运行 (N)」里，
  默认不展开，点开单个运行再显示其摘要与操作。
- 操作保留暂停、恢复（可附带给对方的说明）、续一轮、取消；取消是次要操作并保留确认。**不做
  手工新建或启动**，也不编辑绑定或全局模板；双方会话、自动送审、绑定状态、模板仅只读展示。
- 当前会话没有关联触发器时只显示空状态，不提供新建按钮。
- 宿主先按 session 过滤 bindings / runs / deliveries，再套用快照上限；run 的归属取启动时
  快照的 executor/parent，绑定事后改配对不会让在途或历史运行串到别的会话。
- 滚动交给会话的常驻滚动容器（与 Chat 相同），页签内不再自建固定高度滚动层；展开详情后
  底部记录和操作随页面滚动可达。
- 移动端：全部点按、≥44px 目标、`min(px, vw)` 宽度、无 hover-only 行为；颜色与边框使用
  DSH 主题 token，明暗主题共用。页面在挂载期间每 10 秒刷新一次，切到后台暂停轮询，回到前台
  立即补一次。

## 与 dsh-handoff 的接入

handoff 选择界面可勾选「执行完成后自动交回当前 Session 审核」；spawn 流程在发出首条
执行 prompt **之前** 调用本插件的 `triggerBindings` 服务建好绑定并启动 run（顺序：创建
session → 持久关联 → 建绑定 → 首条 prompt），执行者拿到的首条 prompt 自带 runId 与
收尾规则。勾选创建的 run **默认自动送审**（执行者正常结束回合即交付），审核裁决仍走
`trigger_signal` 工具。详见 dsh-handoff README。默认关闭，不勾选时 handoff 行为与从前
完全一致。

## 安装

```sh
pnpm build
dsh plugin --profile <name> add ./packages/triggers
```

或开发 overlay：`dsh --profile web --patch $PWD/packages/triggers/dev.patch.yml --no-open --port <端口>`。

## 配置

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `deliverTimeoutMs` | `120000` | 单次队列投递的等待预算；超时记 failed 并暂停 run |

## 依赖面

- 宿主运行时 peer：`@deepseek-ai/cordis`、`dsh-llm`（defineTool 类型）、`dsh-storage-domain`
  （+ zod，宿主自带）、`dsh-tools`、`schemastery`；`dsh-agent` / `dsh-session` /
  `dsh-api-session-controller` / `dsh-client-connection` / `dsh-host-webserver` 为 type-only。
- 浏览器 half：`client/client.js`（React.createElement，无 JSX），唯一 slot：
  `conversation.view`（id `triggers`，order 30）；通信走 `/dsh-triggers` 前缀路由
  （connection 信封 + webServer）。
- 发布可选服务 `triggerBindings`（`ctx.get('triggerBindings')`）；无 handoff 的组装照常加载。
